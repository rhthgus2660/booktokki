# P5-B Conversation 배포 전 정책

## 관계 상태별 접근

| 상태 | 과거 메시지 | 신규 전송 | 상대 정보 |
| --- | --- | --- | --- |
| 친구 관계 유지 | 조회 가능 | 가능 | 현재 친구 프로필 |
| 친구 끊기 | 당사자만 읽기 전용 | 불가 | 마지막 메시지의 닉네임 snapshot |
| 차단 | 당사자만 읽기 전용 | 불가 | 마지막 메시지의 닉네임 snapshot |
| 재친구 | 과거 대화와 새 대화를 각각 조회 | 새 connection에서만 가능 | 새 관계의 현재 프로필 |

과거 대화 RPC는 해당 connection의 기존 메시지에서 현재 사용자가 sender 또는 recipient인지를 검사한다.
대화 목록은 `friend_profiles`를 조회하지 않고 메시지 전송 시 저장한 닉네임만 사용한다.

## Polling과 Realtime

- 5초 polling: 화면을 연 사용자당 분당 12회, 시간당 720회 조회다.
- 10초 polling: 화면을 연 사용자당 분당 6회, 시간당 360회 조회다.
- polling은 화면이 visible이고 해당 대화 화면이 열렸을 때만 실행하고, background에서는 중단해야 한다.
- 메시지 전송 rate limit과 조회 polling은 별개이므로 polling이 전송 제한을 소비하지 않는다.
- Supabase Realtime은 지연과 호출 수 면에서 유리하지만 publication과 메시지 SELECT/RLS 계약이 추가되어 현재 RPC-only 경계를 넓힌다.

V1 확정안은 **10초 polling + foreground 복귀 시 즉시 1회 조회**다. 대화 화면이 visible인 동안만 동작하며 화면 이탈·background·logout/account switch에서는 중단한다. Realtime은 V1 범위에서 제외한다.

## 보존·삭제

- 메시지 신고 evidence는 신고 접수 시각 기준 최대 90일 보존한다. `pg_cron`이 매시간 제한된 purge RPC를 실행하며 정상 실행 시 89일 23시간부터 90일 미만 사이에 삭제한다.
- 현재 FK는 auth 사용자 삭제 시 관련 메시지를 cascade delete한다. V1에서는 이 정책을 유지하며, 한쪽 계정 삭제 시 상대 화면에서도 공동 대화가 사라질 수 있음을 이용자에게 안내한다.
- 개별 메시지 삭제와 탈퇴자 익명화 보존은 V1 범위에서 제외한다.
- 개인정보 삭제 요청은 현재 계정 삭제 cascade를 따른다. 신고 증거를 별도로 보존하려면 법적 근거·보존 기간·접근 권한을 확정한 별도 구조가 필요하다.
- P5-A 신고는 현재 프로필 snapshot만 저장하며 메시지 증거를 저장하지 않는다. 향후 신고 메시지 snapshot을 추가한다면 일반 대화 삭제와 분리된 접근 통제·보존 기간이 필요하다.

신고 증거는 일반 대화와 분리되며 최대 90일 보존한다. 계정 삭제 cascade가 먼저 발생하면 90일 이전에도 삭제될 수 있다.

## 과거 대화 신고 안전성

P5-A의 `report_friend_connection`은 현재 `friend_links`에서 상대를 찾으므로 친구 끊기·차단 후에는 사용할 수 없다. 차단된 상대의 최신 프로필을 다시 조회해 신고하는 방식은 차단 개인정보 경계를 깨므로 사용하지 않는다.

V1은 과거 대화 화면에서 상대가 보낸 특정 메시지를 선택해 별도 RPC로 신고한다. 서버는 요청 사용자가 해당 메시지의 recipient인지, message와 connection이 일치하는지, 신고 대상 sender가 본인이 아닌지를 검증한다. 신고 시 상대 최신 프로필 대신 메시지에 이미 저장된 닉네임 snapshot과 증거 메시지 본문·작성 시각의 immutable snapshot만 운영자 전용 evidence table에 보존한다.

일반 사용자는 증거 table을 직접 조회할 수 없고 `service_role`도 직접 table 접근은 SELECT만 허용한다. review 상태는 기존 `social_reports`의 제한된 review column을 사용한다. 만료 증거 삭제는 임의 cutoff를 받지 않는 service-role 전용 RPC와 DB 내부 Cron만 사용하며 별도 영구 보존은 구현하지 않는다.

## 실제 모바일 QA 계획

1. 테스트 계정 A/B를 친구로 연결한다.
2. 친구 프로필에서 빈 대화를 열고 A→B, B→A 메시지를 전송한다.
3. 새로고침과 재로그인 후 순서·작성 시각·내용이 유지되는지 확인한다.
4. 네트워크를 끊어 전송 실패 문구와 draft 유지 여부를 확인한다.
5. 친구 끊기 후 양쪽에서 과거 대화가 읽기 전용인지 확인한다.
6. 재친구 후 과거 대화와 새 대화가 별도로 표시되는지 확인한다.
7. 별도 관계에서 차단 후 양쪽의 과거 대화 읽기 전용, 신규 전송 차단, 최신 프로필 비노출을 확인한다.
8. 375px/390px Safari에서 빈 상태, 목록, 긴 메시지, 입력창, 읽기 전용 안내를 확인한다.
9. MY, 친구 프로필, Room, Presence와 기존 Book Log 흐름을 smoke test한다.
